# Roles

A `Role` is a named bundle of authority within one group. Roles carry a `priority` (higher = more authority), an optional color, a flag indicating whether they should be auto-assigned to new members, free-form `metadata`, a list of **entries** (each one grants or denies a permission key), and optional **parent roles** whose entries they inherit. How entries and parents combine into an answer is described on the [permissions reference](/api-reference/permissions) and in [core concepts](/core-concepts#how-a-check-is-resolved).

The group-scoped routes (`POST /v1/groups/:id/roles`, `GET /v1/groups/:id/roles`, `GET /v1/groups/:id/role-graph`) live on this page; so do the by-id routes (`GET /v1/roles/:id`, `PATCH /v1/roles/:id`, `DELETE /v1/roles/:id`), the entry routes (`POST /v1/roles/:id/permissions`, `DELETE /v1/roles/:id/permissions/:permission`, `PUT /v1/roles/:id/entries`), the parent route (`PUT /v1/roles/:id/parents`) and the member access read (`GET /v1/groups/:id/members/:userId/access`).

## Wire format

`Role` is the shape returned by every endpoint that emits it. Timestamps are ISO 8601 strings.

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | Server-generated cuid. |
| `groupId` | string | The group this role belongs to. |
| `name` | string | 1-64 characters. Unique within the group. |
| `priority` | number | Integer. Higher = more authority. Used by the SDK's "can-act-on" helpers. |
| `color` | string \| null | A 7-character hex color (e.g. `"#ff5050"`) if present, null otherwise. |
| `isDefault` | boolean | A per-role flag the dev can set; multiple roles in a group may carry it. The single canonical "default role" lives on `Group.defaultRoleId`. |
| `permissions` | string[] | The keys this role grants globally: every global entry whose `value` is true, sorted by key. Deny entries and entries with a `context` are not listed here. `[]` on a freshly-created role. |
| `entries` | `{ permission: string, value: boolean, context?: object }[]` | Every entry on the role, sorted by key and then by context, with a key's global entry first. `value: true` grants the key, `value: false` denies it. `context` is present only on a [contextual entry](#entries-with-a-context). |
| `parents` | string[] | Ids of the roles this role inherits from, all in the same group, sorted. |
| `metadata` | object | Free-form JSON object, at most 16 KB serialized. `{}` by default. |
| `createdAt` | string | ISO 8601 timestamp. |

```json
{
  "id": "role_vip",
  "groupId": "grp_network",
  "name": "VIP",
  "priority": 40,
  "color": "#e6b800",
  "isDefault": false,
  "permissions": ["chat.color", "shop.*"],
  "entries": [
    { "permission": "chat.color", "value": true },
    { "permission": "shop.*", "value": true },
    { "permission": "shop.refund", "value": false }
  ],
  "parents": ["role_member"],
  "metadata": { "prefix": "[VIP]" },
  "createdAt": "2026-11-05T12:00:00.000Z"
}
```

## Entries with a context

An entry can carry a `context`, such as `{ "world": "creative" }`, so it applies only to checks made in that context. Without one, an entry is global. An entry is identified by its key **and** its context, so one role can hold the same key once globally and once per context:

```json
{
  "entries": [
    { "permission": "essentials.fly", "value": false },
    { "permission": "essentials.*", "value": true, "context": { "world": "creative" } }
  ]
}
```

Context keys match `^[a-z][a-z0-9_]{0,31}$`, an entry carries at most 2 keys, and values are 1 to 64 characters, stored folded to ASCII lowercase in both permission modes. `{}` means global. How contextual entries rank against global ones is described under [contexts](/api-reference/permissions#contexts). Contextual entries count toward the 5,000-entry cap like any other.

Contextual entries are listed only in `entries`, never in the legacy `permissions` list, and changing one emits `role.updated` with `changed: ["entries"]` rather than `permission.granted` or `permission.revoked`: those two events keep describing the global granted set.

## `POST /v1/groups/:id/roles`

Creates a new role inside the named group. Writes a `role.created` audit entry in the same transaction.

### Request

```json
{
  "name": "Officer",
  "priority": 80,
  "color": "#ff5050",
  "isDefault": false
}
```

| Field | Required | Default | Notes |
|-------|----------|---------|-------|
| `name` | yes | | 1-64 characters. Unique within the group. |
| `priority` | yes | | Integer. Negative values are allowed (treat as "deprioritized"). |
| `color` | no | `null` | If present, must match `^#[0-9a-fA-F]{6}$`. |
| `isDefault` | no | `false` | Per-role tag. Multiple roles in one group can carry it. |
| `metadata` | no | `{}` | Free-form JSON object, at most 16 KB serialized. |

In `"nodes"` [permission mode](/api-reference/permissions#permission-modes), `name` must also be unique ignoring case.

`permissions` is intentionally not part of the create body; the grant route (`POST /v1/roles/:id/permissions`, documented below) is the dedicated path for adding permission keys.

### Response

`201 Created` with a `Role` body. `permissions` is always `[]` on a freshly created role.

### Audit log

One `role.created` entry, written in the same transaction:

```json
{
  "groupId": "<groupId>",
  "actorUserId": null,
  "action": "role.created",
  "targetId": "<roleId>",
  "payload": {
    "name": "Officer",
    "priority": 80,
    "color": "#ff5050",
    "isDefault": false
  }
}
```

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Missing required fields, name out of range, priority not an integer, color not a 7-char hex, or malformed JSON. |
| `not_found` | 404 | No group with that id in the calling game (soft-deleted and cross-game collapse here). |
| `role_name_taken` | 409 | Another role in the same group already has that name. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `GET /v1/groups/:id/roles`

Lists every role in a group. Returns a bare array by default (no pagination wrapper); roles are conventionally a small list (10s, not 1000s).

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. URL-decoded by the router. |

### Query parameters

| Field | Type | Default | Notes |
|-------|------|---------|-------|
| `paged` | `"true" \| "false"` | `false` | Wrap the roles in the `{ items, nextCursor }` envelope the other list routes use. Any other value returns `400`. |

### Response

`200 OK` with a `Role[]` body. Items are ordered by `priority` desc with `id` desc as a tiebreaker, so the highest-authority roles appear first. Permissions are batch-loaded for the page.

### The two response shapes

This route is the one list endpoint that answers with a bare array rather than a `Page`. That asymmetry is real, and it is the kind that surfaces as a runtime `TypeError` rather than a compile error when a caller reaches for a shared page helper.

Both halves of the fix are non-breaking:

- **On the wire**, `?paged=true` returns `{ "items": [...], "nextCursor": null }`. The bare array stays the default, because a published client deserializes this route's body as an array and flipping the default would break it against an upgraded server. `nextCursor` is always `null`: the route returns every role in the group, it does not paginate. See [Pagination](/pagination#non-paginated-endpoints).
- **In the TypeScript SDK**, `roles.list()` already returns a value that is *both*. It is a real array, so `.filter` / `.map` / indexing keep working, and it also carries `items` and `nextCursor`. Nothing to opt into. See the [SDK roles reference](/sdk/roles).

Other SDKs return their language's natural collection: a Lua array in Roblox, a `std::vector<Role>` in C++ and Unreal. Neither ecosystem shares page-shaped helpers across list calls the way JavaScript does, so there is no asymmetry there to close.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | `paged` was neither `"true"` nor `"false"`. |
| `not_found` | 404 | No group with that id in the calling game. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `GET /v1/roles/:id`

Fetches a single role by `Role.id`. Scoped to the calling game (a role whose group belongs to a different game returns 404 to avoid leaking existence). A soft-deleted group also 404s.

### Response

`200 OK` with a `Role` body.

### Errors

| Code | Status | When |
|------|--------|------|
| `not_found` | 404 | No role with that id, or the role's group belongs to a different game, or the role's group is soft-deleted. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `PATCH /v1/roles/:id`

Updates one or more fields on an existing role. The body is partial: any subset of `{ name, priority, color, isDefault, metadata }`. Empty body returns `400`. A non-noop PATCH emits a [`role.updated`](#the-roleupdated-event) event naming the changed fields.

Each field is diffed per-field against the stored row. Only fields whose new value differs from stored go into the update statement and the audit `payload`. A no-op PATCH (every supplied value equals the stored one) skips the DB write entirely, returns the unchanged role, and writes no audit entry.

### Request

```json
{
  "priority": 90,
  "color": null
}
```

| Field | Type | Notes |
|-------|------|-------|
| `name` | string | 1-64 chars. Unique within the group; renaming to an existing name returns 409. |
| `priority` | number | Integer. |
| `color` | string \| null | 7-char hex; pass `null` to clear. |
| `isDefault` | boolean | |
| `metadata` | object | Replaces the whole metadata object. At most 16 KB serialized. |

### Response

`200 OK` with the updated `Role` body. `permissions` is loaded fresh.

### Audit log

One `role.updated` entry per non-noop PATCH, with `payload: { before, after }` containing only the changed fields:

```json
{
  "action": "role.updated",
  "targetId": "<roleId>",
  "payload": {
    "before": { "priority": 80, "color": "#ff5050" },
    "after": { "priority": 90, "color": null }
  }
}
```

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Empty body, invalid color, name out of range, or priority not an integer. |
| `not_found` | 404 | Role missing / cross-game / soft-deleted-group. |
| `role_name_taken` | 409 | Renaming to a name already used by another role in the same group. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `DELETE /v1/roles/:id`

Hard-deletes a role. Roles do not have a soft-delete window.

If any `MemberRole` rows reference the role, the request returns `409 role_has_members` and the role is preserved. The caller must reassign affected members (or remove the assignment) before deleting.

On success, writes a `role.deleted` audit entry containing the deleted row's snapshot:

```json
{
  "action": "role.deleted",
  "targetId": "<roleId>",
  "payload": {
    "name": "Officer",
    "priority": 80,
    "color": "#ff5050",
    "isDefault": false
  }
}
```

Roles that inherited from the deleted role lose it as a parent, and each gets a [`role.updated`](#the-roleupdated-event) event with `changed: ["parents"]`.

### Response

`204 No Content` on success.

### Errors

| Code | Status | When |
|------|--------|------|
| `role_has_members` | 409 | The role has at least one `MemberRole` assignment. Reassign first. |
| `not_found` | 404 | Role missing / cross-game / soft-deleted-group. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `POST /v1/roles/:id/permissions`

Adds or changes one entry on a role. Without `value`, or with `value: true`, the entry grants the key; with `value: false` it denies it. The route is idempotent: writing an entry the role already holds with the same value returns the unchanged role with no audit entry and no DB write.

The first time a permission key is written on a given game, it is auto-registered into `PermissionDef` (the per-game catalog of "known keys" the dashboard and SDK validators consult). Subsequent writes of the same key reuse the existing `PermissionDef` row; removing the entry later does not remove the def.

### Request

```json
{ "permission": "invite_member" }
```

```json
{ "permission": "shop.refund", "value": false }
```

```json
{ "permission": "essentials.fly", "value": true, "context": { "world": "creative" } }
```

| Field | Required | Notes |
|-------|----------|-------|
| `permission` | yes | 1-128 characters. Free-form string; the dev defines their own keys. In `"nodes"` mode it is lowercased and must pass the [key rules](/api-reference/permissions#permission-modes). |
| `value` | no | Boolean, default `true`. `false` stores a deny entry. |
| `context` | no | The entry's [context](#entries-with-a-context). Absent or `{}` writes the global entry. |

A role holds at most 5,000 entries, contextual ones included; adding a new entry to a full role returns `400`.

### Events

For a global entry:

- A key that becomes granted emits `permission.granted`.
- A grant that becomes a deny emits `permission.revoked` and then `role.updated`.
- A new deny entry emits `role.updated` only.

Any change to a contextual entry emits `role.updated` with `changed: ["entries"]` only.

### Response

`200 OK` with the updated `Role` body. `permissions` reflects the post-state and is sorted by key.

### Audit log

One `permission.granted` entry per write that makes a global key granted (a deny turned into a grant adds `"before": { "value": false }` to the payload). Writes that store a deny, and every write to a contextual entry, record a `role.entries.changed` entry instead, with the same diff payload as [`PUT /v1/roles/:id/entries`](#put-v1rolesidentries).

```json
{
  "action": "permission.granted",
  "targetId": "<roleId>",
  "payload": {
    "roleId": "<roleId>",
    "permission": "invite_member"
  }
}
```

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Missing or empty `permission`, key over 128 characters, an invalid `context`, or malformed JSON. |
| `not_found` | 404 | Role missing / cross-game / soft-deleted-group. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `DELETE /v1/roles/:id/permissions/:permission`

Removes the role's entry for a key, whether it grants or denies. Without context query parameters it removes the **global** entry; `context.<key>=<value>` parameters select a contextual one instead (`DELETE /v1/roles/role_admin/permissions/essentials.fly?context.world=creative`). The route is idempotent: removing an entry the role does not have returns the unchanged role with no audit entry. In `"nodes"` mode the key is lowercased before lookup, and context values are folded in both modes. The `PermissionDef` registry is preserved (removal does not "forget" the key for the game).

Removing a global grant emits `permission.revoked` and records a `permission.revoked` audit entry. Removing a global deny, or any contextual entry, emits `role.updated` and records `role.entries.changed`.

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The role id. URL-decoded by the router. |
| `permission` | string | The permission key. URL-decoded by the router. |

### Query parameters

| Field | Required | Notes |
|-------|----------|-------|
| `context.<key>` | no | One per context key of the entry to remove. Absent targets the global entry. |

### Response

`200 OK` with the updated `Role` body. `permissions` reflects the post-state.

### Audit log

One `permission.revoked` entry per non-noop revoke:

```json
{
  "action": "permission.revoked",
  "targetId": "<roleId>",
  "payload": {
    "roleId": "<roleId>",
    "permission": "invite_member"
  }
}
```

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | A `context.<key>` parameter is invalid or repeated. |
| `not_found` | 404 | Role missing / cross-game / soft-deleted-group. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `PUT /v1/roles/:id/entries`

Replaces a role's whole entry list in one transaction. Entries are matched by key and context: entries not in the list are removed, entries whose value changes are updated, and new entries are added (and their keys registered in the catalog). A request that changes nothing writes nothing.

### Request

```json
{
  "entries": [
    { "permission": "*", "value": true },
    { "permission": "chat.mute.exempt", "value": false },
    { "permission": "shop.admin.*", "value": false },
    { "permission": "shop.admin.*", "value": true, "context": { "world": "market" } }
  ]
}
```

| Field | Required | Notes |
|-------|----------|-------|
| `entries` | yes | Array of at most 5,000 `{ permission, value, context? }` objects. Each `(permission, context)` pair may appear once: a key may appear once globally and once per distinct context. In `"nodes"` mode keys are lowercased first, and context values are folded in both modes, so two spellings of one pair are duplicates. `[]` clears the role. |

### Response

`200 OK` with the updated `Role` body.

### Audit log and events

One `role.entries.changed` audit entry per non-noop replace, carrying the diff:

```json
{
  "action": "role.entries.changed",
  "targetId": "<roleId>",
  "payload": {
    "roleId": "<roleId>",
    "added": [{ "permission": "shop.admin.*", "value": false }],
    "removed": [{ "permission": "shop.legacy", "value": true }],
    "changed": [{ "permission": "chat.mute.exempt", "before": true, "after": false }]
  }
}
```

A contextual entry in the diff carries its `context` beside `permission`.

One `role.updated` event with `changed: ["entries"]`. A replace does not emit per-key `permission.granted` / `permission.revoked` events.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Malformed body, over 5,000 entries, a duplicate `(permission, context)` pair, a key over 128 characters, a key that breaks the `"nodes"` key rules, or an invalid `context`. |
| `not_found` | 404 | Role missing / cross-game / soft-deleted-group. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## Role parents

A role inherits the entries of its parent roles, one layer further from the member than the role itself; a parent's parents sit one layer further again. The first layer with a matching entry decides a check, so a role's own entries always beat what it inherits. A role reachable through several paths counts at its shortest distance.

Limits: up to 32 parents per role, and inheritance chains up to 100 levels deep. Parents must be in the same group. Cycles are rejected when written.

## `PUT /v1/roles/:id/parents`

Replaces a role's whole parent list.

### Request

```json
{ "parents": ["role_member", "role_pet_bundle"] }
```

| Field | Required | Notes |
|-------|----------|-------|
| `parents` | yes | Array of at most 32 role ids. Duplicates are ignored. `[]` clears the role's parents. |

### Response

`200 OK` with the updated `Role` body.

### Audit log and events

One `role.parents.set` audit entry per non-noop write, with `payload: { roleId, before, after }` (sorted id lists), and one `role.updated` event with `changed: ["parents"]`.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Malformed body, over 32 parents, or the change would make an inheritance chain deeper than 100 levels. |
| `parent_cycle` | 400 | The role lists itself, or the change would close a cycle. |
| `role_group_mismatch` | 400 | A parent belongs to another group. |
| `not_found` | 404 | The role or a parent is missing, cross-game, or in a soft-deleted group. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `GET /v1/groups/:id/role-graph`

Everything needed to resolve checks for the group locally, in one read: the game's permission mode and context inheritance, the group's default role, and every role with its entries, parents and metadata. Roles are ordered by priority descending, then id descending.

```json
{
  "groupId": "grp_network",
  "mode": "nodes",
  "contexts": {
    "world": { "inherit": { "pvpworld": ["world"] } }
  },
  "defaultRoleId": "role_default",
  "roles": [
    {
      "id": "role_admin",
      "groupId": "grp_network",
      "name": "Admin",
      "priority": 100,
      "color": null,
      "isDefault": false,
      "permissions": ["*"],
      "entries": [{ "permission": "*", "value": true }],
      "parents": ["role_vip"],
      "metadata": {},
      "createdAt": "2026-11-05T12:00:00.000Z"
    }
  ]
}
```

| Field | Type | Notes |
|-------|------|-------|
| `groupId` | string | The group. |
| `mode` | `"exact"` \| `"nodes"` | The game's [permission mode](/api-reference/permissions#permission-modes). |
| `contexts` | object | The game's [context inheritance](/api-reference/admin#permission-contexts), with folded values; `{}` when the game declares none. Game-wide, so every group's graph carries the same value. Servers that predate the field omit it; read it as `{}`. |
| `defaultRoleId` | string \| null | The group's default role. |
| `roles` | `Role[]` | Each element is a full [`Role`](#wire-format). |

The response carries the `Junjo-Stream-Position` header (see [Snapshots and the stream](/api-reference/events#snapshots-and-the-stream)). A change to `mode` or `contexts` arrives on the game stream as `permissions.config.updated`; the game's own key can also read both alone with [`GET /v1/permissions/config`](/api-reference/permissions#get-v1permissionsconfig).

Returns `404 not_found` for a missing, cross-game or soft-deleted group.

## `GET /v1/groups/:id/members/:userId/access`

One member's inputs to resolution, in one read: their status, the roles they hold directly, their overrides and their metadata. Roles reached through inheritance come from the role graph.

```json
{
  "groupId": "grp_network",
  "userId": "user_alice",
  "status": "active",
  "roleIds": ["role_vip"],
  "overrides": [
    {
      "groupId": "grp_network",
      "userId": "user_alice",
      "permission": "chat.color",
      "grant": false,
      "setAt": "2026-11-05T12:00:00.000Z",
      "setBy": null
    },
    {
      "groupId": "grp_network",
      "userId": "user_alice",
      "permission": "chat.color",
      "grant": true,
      "context": { "world": "hub" },
      "setAt": "2026-11-05T12:05:00.000Z",
      "setBy": null
    }
  ],
  "version": 4,
  "displayName": "Alice",
  "metadata": { "prefix": "[VIP]" }
}
```

`version` is the member's [version](/api-reference/groups#member-versions), also sent as the `ETag` header, so an access snapshot can be paired with conditional writes.

Only `active` members exercise permissions; the status is returned so a local resolver can apply the same gate. Returns `404 not_found` when the group, the user's identity, or the membership row does not exist.

## `POST /v1/groups/:id/members/access`

The same read for up to 100 users in one request, for a cache that loads many members at once (a game server after a restart, for example).

```json
{ "userIds": ["mc:2f0c6a1e-0b6f-4f0e-9c1a-5d2b7e8f9a10", "mc:9d3b1c2a-4e5f-4a6b-8c7d-0e1f2a3b4c5d"] }
```

The answer lines up with `userIds`: entry `i` is the access object for `userIds[i]`, or `null` when that id names no member of the group. Any of a person's linked ids finds them; the object names the person by your [rendering rule](/api-reference/identity#the-rendering-rule), so match entries by position, not by `userId`.

```json
{ "items": [{ "groupId": "grp_network", "userId": "mc:2f0c6a1e-0b6f-4f0e-9c1a-5d2b7e8f9a10", "status": "active", "roleIds": ["role_vip"], "overrides": [], "version": 4, "displayName": "Alice", "metadata": {} }, null] }
```

The response carries `Junjo-Stream-Position`, read before the data (see [snapshots and the stream](/api-reference/events#snapshots-and-the-stream)), and no `ETag`; each item carries its own `version`. One to 100 ids, otherwise `400 bad_request`. `404 not_found` when the group does not exist.

## The `role.updated` event

`role.updated` is a group-scoped event delivered over SSE and webhooks. It is a change signal: it says which parts of a role changed, not their new values, so consumers re-read the role or the role graph.

```json
{
  "type": "role.updated",
  "id": "a41c9e07d2b85f3e6c10d4a7",
  "occurredAt": "2026-11-05T12:00:00.000Z",
  "gameId": "game_...",
  "groupId": "grp_network",
  "roleId": "role_vip",
  "changed": ["entries"]
}
```

`changed` lists any of `name`, `priority`, `color`, `isDefault`, `metadata`, `entries`, `parents`. Single-route changes that only add or remove a global grant emit `permission.granted` / `permission.revoked` and no `role.updated`; any change to a contextual entry emits `role.updated` with `changed: ["entries"]`.
