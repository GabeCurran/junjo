# Error codes

Every non-2xx response from the Junjo server uses the same envelope:

```json
{
  "code": "<snake_case_code>",
  "status": <http_status>,
  "message": "<human-readable explanation>",
  "requestId": "<correlation id, when present>",
  "details": { "<structured detail, when present>": "..." }
}
```

`requestId` is a correlation id, present on internal-500 responses; it matches the `x-request-id` response header, which the server sets on every response. Quote it in bug reports so a specific failed request can be found in the server logs.

`details` is present only on errors that carry structured information:

| Where | `details` |
|-------|-----------|
| [`POST /v1/groups/:id/members/import`](/api-reference/groups#post-v1groupsidmembersimport) (`400` / `403` / `409`) | `{ "rows": [{ "index", "userId", "code", "message" }] }`, one entry for every failing row. |
| `DELETE /v1/bans/:userId` and `DELETE /v1/groups/:id/members/:userId/ban` (`404`) | `{ "reason": "not_active" }` when there is no active ban to lift. Other `404`s on those routes (an unknown group) have no `details`. |
| [`DELETE /v1/sanctions/:userId/:type`](/api-reference/sanctions#delete-v1sanctionsuseridtype) (`404`) | `{ "reason": "not_active" }` when there is no active sanction of that type to lift. |
| `PATCH /v1/groups/:id` and `DELETE /v1/groups/:id` (`412`) | `{ "version": "<current>" }`, the group's current [version](/api-reference/groups#group-versions), when `If-Match` named another one. |
| `POST /v1/groups/:id/members` with `If-None-Match: *` (`412`) | `{ "memberStatus": "<status>" }`, the status of the membership row that already exists. |

The TypeScript SDK preserves the envelope on the `JunjoError` it throws, so callers can branch on `error.code` instead of parsing strings:

```ts
import { JunjoError } from "@junjo.io/sdk";

try {
  await junjo.groups.get(groupId);
} catch (err) {
  if (err instanceof JunjoError && err.code === "not_found") {
    return null;
  }
  throw err;
}
```

This page is the canonical inventory. Per-resource pages mention the codes they raise; this page lists every code that the server or the SDK can produce.

## Server codes

These are returned by the Junjo server (`packages/server`) and round-trip through the SDK as `JunjoError` instances with the same `code` and `status`. The authoritative list is `JUNJO_ERROR_CODES` in `packages/shared/src/types.ts`.

| code | status | when it is raised | how to handle |
|------|--------|-------------------|---------------|
| `bad_request` | 400 | Body or query parameters failed Zod validation, or a string anywhere in the request (an id, a reason, a metadata value) contains the NUL character U+0000, which cannot be stored. Also raised for semantic input errors that are not domain-specific (e.g. unknown `kind` on `groups.create`), for a malformed `Idempotency-Key`, [`Junjo-Write-Tag`](/api-reference#write-tags) or `If-Match` header (nothing is written), for an `If-None-Match` header other than `*`, and for a member import with failing rows (listed in `details.rows`). | Fix the request shape. The `message` field describes which field failed. |
| `parent_cycle` | 400 | `PUT /v1/groups/:id/parent` was called with a parent id that would create a cycle in the group parent chain, or `PUT /v1/roles/:id/parents` listed the role itself or would close a cycle among role parents. | Pick a different parent or restructure the hierarchy. |
| `invalid_user_id` | 400 | A user id (path, query or body, on any route including reads and admin routes) is in a namespace whose game declares a [canonical format](/api-reference/identity#canonical-formats), and does not match it. Bulk invite reports such rows as per-row errors instead. | Normalize the id to the declared format (for `uuid`: lowercase, hyphenated) before sending it. |
| `link_code_invalid` | 400 | `POST /v1/link-codes/redeem` was given a code that is unknown, expired, already used, or not shaped like a code. One answer for every case. | Ask the person to request a new code. Repeated failures spend the key's failed-redeem budget and end in `429`. |
| `role_group_mismatch` | 400 | Tried to assign a role to a member of a group the role does not belong to, to set a role parent from another group, or to perform a similar cross-group operation on roles. | Pass a role id that belongs to the same group. |
| `invalid_api_key` | 401 | API key missing, malformed, unknown, or revoked. | Check the `Authorization: Bearer <prefix>.<secret>` header. Issue a new key if the secret was lost. |
| `invalid_admin_token` | 401 | Admin endpoint called with a missing or wrong admin token. Also returned when the server has `JUNJO_ADMIN_TOKEN` unset (admin endpoints are disabled on that deployment). See [Admin](/api-reference/admin). | Set `JUNJO_ADMIN_TOKEN` on the server and pass it as `Authorization: Bearer <token>`. |
| `permission_denied` | 403 | Caller lacks permission to perform the action. Also `GET /v1/export` with a key that does not have `canExport`. | The action is intentional refusal, not a missing resource. Either grant the caller the required permission or have a different actor perform the call. |
| `banned` | 403 | The user is banned from the group (or game-wide) and tried to join or accept an invitation, or every failing row of a member import is a ban (`details.rows`). See [Bans](/api-reference/bans). Also returned by link-code request, redeem and unlink when a person involved is banned; see [Identity](/api-reference/identity). | Surface the refusal to the user. Lift the ban first if the join should succeed. |
| `passcode_required` | 403 | The group requires a passcode to join and none was supplied on `POST /v1/groups/:id/join`. | Prompt the user for the passcode and retry with it. |
| `passcode_invalid` | 403 | A passcode was supplied on join but does not match the group's passcode. | Prompt again. Do not retry automatically. |
| `not_found` | 404 | Resource does not exist or is soft-deleted. Also returned for every friends route when `friends.enabled = false`, so feature absence is invisible. A ban or sanction lift with nothing active to lift adds `details.reason: "not_active"`. | The SDK turns `not_found` from `groups.get` and a few other read endpoints into `null`; for mutations it surfaces as a thrown `JunjoError`. Treat as "no such resource". For `not_active` on a replayed lift, see [Safe retries](/api-reference#safe-retries-for-queued-writes). |
| `idempotency_key_in_progress` | 409 | A request with the same [`Idempotency-Key`](/api-reference#idempotency-keys) from the same API key is still running. Carries `Retry-After: 1`. | Wait and retry with the same key and the same request; the retry gets the first request's answer. |
| `already_member` | 409 | Tried to invite, accept an invitation for, or otherwise add a user who is already an active `GroupMember` of the group. Also the loser's outcome when two concurrent joins race. | Idempotent on the caller side: if the goal is "make sure user is a member", check membership first or treat 409 as success. |
| `group_full` | 409 | A join, add, invitation accept or import would take a group past its kind's `maxMembers` ([Kind limits](/api-reference/groups#kind-limits)). An import answers it when every failing row is `group_full`. | Surface "this group is full". Retrying succeeds only once someone leaves. |
| `group_limit_reached` | 409 | The user already holds the kind's `maxPerUser` active memberships, on join, add, invitation accept, import, or group creation with `creatorUserId`. | Have the user leave one of their groups of that kind first. |
| `role_has_members` | 409 | `DELETE /v1/roles/:id` was called on a role that still has members assigned. | Reassign the affected members to a different role first, then retry the delete. |
| `role_name_taken` | 409 | Tried to create or rename a role to a name that another role in the same group already uses (ignoring case in `"nodes"` permission mode). | Pick a different name. Role names are unique per group, not globally. |
| `permission_mode_conflict` | 409 | A game config change to `permissions.mode` was refused because stored permission keys or role names would change meaning under the new mode. The message names the first few offenders. See [Permission modes](/api-reference/permissions#permission-modes). | Fix or remove the named keys (or rename the roles), then retry the switch. |
| `identity_format_conflict` | 409 | A game config change declared (or changed) a format in `identity.formats` while stored ids in that namespace do not match it. The message lists up to 5 of them. See [Canonical formats](/api-reference/identity#canonical-formats). | Fix or unlink the named ids, then retry the declaration. |
| `link_refused` | 409 | A link code redeem was refused because both ids belong to people that [hold something](/api-reference/identity#who-keeps-their-person) (roles, relationships, history, other ids). The code is not spent. | Do not retry. Merging two established people is a manual operation; clear one side first if the link should succeed. |
| `precondition_failed` | 412 | `If-Match` names a member, group or moderation version other than the current one (for a [group version](/api-reference/groups#group-versions) on `PATCH` or `DELETE /v1/groups/:id`, the current one is in `details.version`), or `If-None-Match: *` on `POST /v1/groups/:id/members` found an existing membership row (its status is in `details.memberStatus`). Nothing was written. See [Conditional writes](/api-reference#conditional-writes) and [Create-only adds](/api-reference/groups#create-only-adds). | For `If-Match`: re-read the member, the group or the person's moderation (`GET /v1/users/:userId/moderation`), decide whether the write still applies, and resend with the new version. For a create-only add: the person is already in the group, so leave the membership as it is. |
| `idempotency_key_reused` | 422 | The `Idempotency-Key` was already used by the same API key for a request with a different method, path, query or body, within the last 24 hours. | Use a fresh key for each distinct write. |
| `invitation_expired` | 410 | The invitation code is past its `expiresAt`. | Issue a new invitation. |
| `invitation_used` | 410 | The invitation was already accepted, declined, or revoked. Also the loser's outcome when two concurrent accepts race on the same invitation. | Issue a new invitation. |
| `restore_window_expired` | 410 | `POST /v1/groups/:id/restore` was called more than 7 days after the soft-delete. | The group is no longer recoverable; create a new one if needed. |
| `too_many_streams` | 429 | Opening a [game stream](/api-reference/events#get-v1events) would exceed 10 open game streams for the key or 200 for the game, or opening a [group stream](/api-reference/events#get-v1eventsgroupid) would exceed 500 open group streams for the key or 2,000 for the game, on the server instance that answered. | Close streams you no longer need. Do not retry in a loop: the limit frees up only when a stream closes. |
| `stream_position_expired` | 410 | The `Last-Event-ID` sent to the [game stream](/api-reference/events#resuming) names a position the event log can no longer serve in full: older than retention (24 hours by default) or ahead of the game. | Load a fresh snapshot, then subscribe from that snapshot's position. |
| `rate_limit_exceeded` | 429 | A rate-limit bucket is empty (per-source or per-API-key, or one of the [link-code buckets](/api-reference/identity#rate-limits)). The response carries a `Retry-After` header (seconds, integer >= 1); the SDK surfaces it as `JunjoError.retryAfterSeconds`. Tunable via `RATE_LIMIT_PER_MINUTE` and `RATE_LIMIT_BURST`. | Back off for at least `Retry-After` seconds. The SDK never retries automatically; honor `retryAfterSeconds` in your own backoff. |
| `internal` | 500 | Unhandled server error. The full error is logged server-side; the response body is generic on purpose and carries a `requestId` for correlation. | Treat as transient. Retry with backoff once or twice; if it persists, check server logs for the `requestId`. |

## SDK codes

These codes are produced by the TypeScript SDK itself: transport failures, client construction problems, wire-format problems, and webhook verification failures. The authoritative list is `JUNJO_SDK_ERROR_CODES` in `packages/sdk/src/errors.ts`. `JunjoError.status` is set only when an HTTP response was actually received; for the webhook verification codes the SDK documents `400` as the status a receiver should respond with.

| code | status | when it is raised | how to handle |
|------|--------|-------------------|---------------|
| `network_error` | none | `fetch` itself rejected: DNS failure, connection refused, TLS error, offline. The request may or may not have reached the server. | Retry with backoff if the operation is idempotent; otherwise reconcile state first. |
| `timeout` | none | The configured `timeoutMs` (default 30000, or a per-request override) elapsed before the response arrived. SSE subscriptions are exempt. | Same caution as `network_error`: the server may have processed the request. |
| `cancelled` | none | The caller's `AbortSignal` aborted the request. | Expected control flow; usually nothing to handle. |
| `invalid_config` | none | Client construction or adapter options were invalid: missing or `jadm_`-shaped `apiKey`, `apiKey` passed in proxy mode, `proxy: true` without `baseUrl`, `inviteByLink` without `inviteBaseUrl`, `verifyToken` without an `authAdapter`, a `writeTag` that is not 1 to 128 printable ASCII characters without spaces, or an auth adapter constructor called with bad arguments. No request was made. | Fix the setup. The `message` field names the field at fault. |
| `invalid_wire_data` | varies | A 2xx response carried a body the SDK could not parse or that failed wire validation (malformed JSON, invalid timestamps, missing SSE body). | Usually an intermediary mangled the response, or client and server versions have drifted far apart. |
| `stream_overflow` | none | An SSE frame exceeded the subscribe buffer cap; the stream is closed. | Resubscribe. If it recurs, an intermediary is likely rewriting the stream. |
| `unknown_event_type` | 400 | An event carried a type this SDK version does not know. `verifyWebhook` throws it; `verifyWebhookWithMeta` throws it too unless called with `onUnknownType: "raw"`, which returns the verified payload verbatim instead. The SSE subscribe loop skips the frame, so a newer server cannot kill older clients' streams. The C++ SDK's `verify_webhook` never raises this: it returns unknown types verbatim. | Match-all endpoints should use `verifyWebhookWithMeta` with `onUnknownType: "raw"` and acknowledge unknown types; otherwise upgrade the SDK. |
| `webhook_signature_missing` | 400 | `verifyWebhook` was called and the request had no `x-junjo-signature` header. | Reject the request. Returning 400 is the right HTTP response. |
| `webhook_timestamp_missing` | 400 | Same, but for the `x-junjo-timestamp` header. | Same as above. |
| `webhook_timestamp_invalid` | 400 | The `x-junjo-timestamp` header value is not a parseable timestamp. Checked after the signature, so unauthenticated probes cannot reach it. | Reject. The sender is not a real Junjo deployment, or the proxy mangled the header. |
| `webhook_timestamp_out_of_tolerance` | 400 | The signed timestamp is more than `tolerance` ms (default 5 minutes) away from the receiver's clock. Defends against replay attacks. | Reject. If clocks are legitimately skewed, fix the receiver clock; do not widen the tolerance. |
| `webhook_invalid_signature` | 400 | The HMAC of `<timestamp>.<body>` does not match the `x-junjo-signature` header. | Reject. The body was tampered with or the secret is wrong. Do NOT log the body or signature; they may contain sensitive data. |
| `webhook_invalid_body` | 400 | The body is not parseable as JSON after the signature check passed. | Reject. An upstream proxy mangled the body, or the sender signed malformed JSON. |
| `webhook_verification_failed` | 400 | Catch-all used by the Express-style `middleware` when verification throws something other than a `JunjoError`. Direct `verify` callers see the specific codes above instead. | Reject the request. |
| `unknown` | varies | A non-2xx response that did not carry the Junjo error envelope (e.g. an HTML 502 from an intermediary proxy). `status` carries the transport status. | Inspect `error.status` to distinguish a proxy-level 5xx (retry with backoff) from a 4xx (do not retry). |

## Retries and Retry-After

The SDK never retries automatically. On `429 rate_limit_exceeded` the server sends a `Retry-After` header (integer seconds), which the SDK surfaces as `JunjoError.retryAfterSeconds`; honor it in your own backoff loop. For transport-level failures (`network_error`, `timeout`) remember that the request may have reached the server, so only blind-retry idempotent operations.

## Forward compatibility

A newer server may introduce error codes this SDK version does not know. Unknown codes pass through at runtime with their status and message intact, so an exhaustive `switch` over `err.code` must keep a `default` branch rather than treating unrecognized codes as impossible.

## SDK type

The `JunjoError` class is exported from the top-level entry of `@junjo.io/sdk`:

```ts
import { JunjoError } from "@junjo.io/sdk";

class JunjoError extends Error {
  readonly code: string;
  readonly status?: number;
  readonly requestId?: string;
  readonly retryAfterSeconds?: number;
  // `message` is inherited from Error
}
```

`status` is optional because transport and config codes have no HTTP status. For codes that originate on the server, `status` is always populated. `requestId` (when present) matches the server's `x-request-id` header and is worth quoting in bug reports. `retryAfterSeconds` is set on rate-limited responses.

## Adding a new code

If you are extending the server with a new error condition, add the code to `JUNJO_ERROR_CODES` in `packages/shared/src/types.ts`, a factory to `packages/server/src/errors.ts`, and a row to the table above. Codes are `snake_case`, scoped narrowly enough that callers can branch on them, and stable: a code that has shipped should not change meaning. Renaming a code is a breaking change for SDK callers.
