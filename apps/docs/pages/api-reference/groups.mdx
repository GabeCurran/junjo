# Groups

A `Group` is the unit Junjo organizes players around: guild, clan, faction, party, crew. The dev's UI labels it however they want; Junjo stores the dev-supplied `kind` string verbatim and never branches on it.

## Wire format

`Group` is returned in this shape on every endpoint that emits it. Timestamps are ISO 8601 strings (the SDK rehydrates them into `Date` instances on the client).

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | Server-generated cuid. |
| `gameId` | string | The game that owns the group. Always equal to the calling key's game. |
| `kind` | string | Dev-defined taxonomy ("guild", "clan", "faction", ...). Stored verbatim. |
| `name` | string | Display name. |
| `visibility` | `"public" \| "invite-only" \| "secret"` | See `POST /v1/groups`. |
| `metadata` | object | Free-form JSON. The dev's bag for motto, banner URL, etc. |
| `defaultRoleId` | string \| null | Role automatically assigned to new members; null until set. |
| `memberCount` | number | Cached count of active members. `0` for a freshly created group. |
| `hasPasscode` | boolean | `true` when a join passcode is set. The plaintext passcode is never returned; callers use this flag to know whether `groups.join` needs a `passcode` field. See [Passcodes](#passcodes). |
| `createdAt` | string | ISO 8601 timestamp. |
| `updatedAt` | string | ISO 8601 timestamp. |
| `softDeletedAt` | string \| null | Set when the group is soft-deleted; null otherwise. |
| `version` | string | The group's [version](#group-versions), a decimal string. Present on single-group responses (get, create, update, delete, restore), which also send it as `ETag`. Absent on `GET /v1/groups` items and on the `group` inside events. |

## Kind limits

A game can set limits per group kind in its config (`groups.kinds`, edited with [`PATCH /v1/admin/games/:gameId/config`](/api-reference/admin) or the dashboard). Junjo ships no defaults: a kind that is not listed has no limits.

```json
{
  "groups": {
    "kinds": {
      "party": { "maxMembers": 8, "maxPerUser": 1, "deleteWhenEmpty": true, "idleDeleteHours": 24 }
    }
  }
}
```

| Field | Range | Effect |
|-------|-------|--------|
| `maxMembers` | 1 to 100000 | Active members one group of the kind may hold. Over the cap: `409 group_full`. |
| `maxPerUser` | 1 to 1000 | Active memberships one person may hold across live (not soft-deleted) groups of the kind. Over the cap: `409 group_limit_reached`. |
| `deleteWhenEmpty` | boolean | When a leave, kick or ban removes the last active member, the same transaction soft-deletes the group (audit `group.deleted` with `reason: "empty"`) and emits `group.deleted`. A write that removes no active member never deletes. |
| `idleDeleteHours` | 1 to 8760 | A background sweeper (every 10 minutes) soft-deletes live groups of the kind whose membership has not changed for that long (audit `reason: "idle"`, event `group.deleted`). |

Every field is optional. At most 32 kinds may be listed; a kind name is 1 to 64 characters, like `kind` on create.

### Where the caps apply

The caps are checked on these paths:

- Join, add (`POST /v1/groups/:id/members`), invitation accept and [import](#post-v1groupsidmembersimport) check `maxMembers` and `maxPerUser`. A refused invitation accept leaves the invitation unused.
- Create with `creatorUserId` checks `maxPerUser`.
- Restoring a soft-deleted group checks `maxPerUser`. When any of its active members has since reached the kind's cap elsewhere, the restore answers `409 group_limit_reached` with `details.members`, how many members are affected. The group stays deleted until they leave a group.
- An [identity link](/api-reference/identity#who-keeps-their-person) checks `maxPerUser`. When the merged person would hold more groups of a kind than the cap, the link answers `409 link_refused`. A merge cannot break `maxMembers`, because every moved membership was already counted by its group.

Re-adding someone who is already an active member is not a new membership and is never refused. Checks run under a lock on the group (and, for `maxPerUser`, on the person within the kind), so concurrent joins cannot overshoot a cap. Group creation has no kind-specific limit; it is covered by the general per-key rate limit.

### Membership activity

Each group tracks when its membership last changed: a member joining, being added, accepting an invitation, being imported, leaving, being kicked, banned or unbanned. Edits to the group itself (name, metadata) do not count. Restoring a soft-deleted group starts a fresh idle period.

### Config patches

`groups.kinds` is stated in full: a `PATCH` that sends `kinds` replaces the stored map, the same as `identity.formats`, so removing a kind from the map removes its limits. A patch that does not send `groups` leaves it alone. Lowering a cap does not remove members already over it; it only refuses new activations.

## `POST /v1/groups`

Creates a new group scoped to the calling game. Writes a `group.created` audit entry in the same transaction.

### Request

```json
{
  "kind": "guild",
  "name": "Crimson Wolves",
  "visibility": "invite-only",
  "metadata": { "motto": "Howl together" },
  "defaultRoleId": "role_xyz"
}
```

| Field | Required | Default | Notes |
|-------|----------|---------|-------|
| `kind` | yes | | 1-64 characters. Dev-defined taxonomy string. |
| `name` | yes | | 1-120 characters. Not unique. |
| `visibility` | no | `"invite-only"` | One of `"public"`, `"invite-only"`, `"secret"`. |
| `metadata` | no | `{}` | Arbitrary JSON object. |
| `defaultRoleId` | no | null | Pre-assigned role for new members. The role must exist on this group; the server does not verify this on create (a defensive existence check is a post-V1 idea). |
| `passcode` | no | none | Optional shared-secret join gate. 4-128 chars. Stored as a scrypt hash; the plaintext is never returned. Members joining via `groups.join` must supply the same string. Orthogonal to `visibility`: a public group with a passcode is "discoverable but gated". See [Passcodes](#passcodes). |
| `creatorUserId` | no | none | Optional external user id of the group's creator. When supplied, the create call atomically adds them as an active `GroupMember` in the same transaction, writes a second audit entry (`member.joined` with `payload.via = "creator"`), and fires the `member.joined` webhook event. Works for every visibility, so creators of `"invite-only"` and `"secret"` groups don't need a separate join call. If `defaultRoleId` is set AND a `Role` row with that id already exists in the new group, that role is assigned to the creator in the same transaction; otherwise the role assignment is silently skipped. |

A missing or malformed body returns `400 bad_request` with the failing path in the message (e.g., `name: required`). A malformed JSON body also returns `400 bad_request`.

### Response

`201 Created` with a `Group` body and the group's [version](#group-versions) as `ETag`:

```json
{
  "id": "ckxxx...",
  "gameId": "ckyyy...",
  "kind": "guild",
  "name": "Crimson Wolves",
  "visibility": "invite-only",
  "metadata": { "motto": "Howl together" },
  "defaultRoleId": "role_xyz",
  "memberCount": 0,
  "hasPasscode": false,
  "createdAt": "2026-04-28T05:00:00.000Z",
  "updatedAt": "2026-04-28T05:00:00.000Z",
  "softDeletedAt": null,
  "version": "0"
}
```

Creating a group emits no event, so a new group is at version `"0"`. With `creatorUserId` the create emits `member.joined`, and the version is that event's position.

### Audit log

Every successful create writes one `group.created` entry. When `creatorUserId` is supplied, a second `member.joined` entry is written in the same transaction.

| Field | Value |
|-------|-------|
| `action` | `group.created` |
| `groupId` | the new group id |
| `targetId` | the new group id |
| `actorUserId` | `null` (server-to-server creation; user actors arrive in later phases) |
| `payload` | `{ kind, name, visibility, metadata, defaultRoleId }` |

When `creatorUserId` is supplied, a follow-up entry:

| Field | Value |
|-------|-------|
| `action` | `member.joined` |
| `groupId` | the new group id |
| `targetId` | the creator's external user id |
| `actorUserId` | the creator's resolved JunjoUser id |
| `payload` | `{ memberId, via: "creator" }`, plus `roleId` when a default role was assigned |

### Webhook event

When `creatorUserId` is supplied, the create call also fires `member.joined` (same shape as the invitation-accept and public-join flows).

## `GET /v1/groups/:id`

Fetches a single group by id. Soft-deleted groups and groups belonging to a different game return `404 not_found` (the route does not leak existence across game boundaries).

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. |

### Query parameters

| Field | Type | Default | Notes |
|-------|------|---------|-------|
| `viewer` | string | none | Optional external user id. When supplied, a group with `visibility = "secret"` returns `404` unless `viewer` is an active member. Omitting it is a server-to-server / admin call and bypasses the secret-group filter. |

### Response

`200 OK` with a `Group` body and the group's [version](#group-versions) as `ETag`. `memberCount` is the number of `GroupMember` rows with `status = "active"` for this group, computed at request time.

```
ETag: "4211"
```

```json
{
  "id": "ckxxx...",
  "gameId": "ckyyy...",
  "kind": "guild",
  "name": "Crimson Wolves",
  "visibility": "invite-only",
  "metadata": { "motto": "Howl together" },
  "defaultRoleId": "role_xyz",
  "memberCount": 42,
  "hasPasscode": false,
  "createdAt": "2026-04-28T05:00:00.000Z",
  "updatedAt": "2026-04-28T05:00:00.000Z",
  "softDeletedAt": null,
  "version": "4211"
}
```

The version is read before the group, so it never runs ahead of the data returned with it. A write that lands in between can make a later `If-Match` with this version fail, never pass on stale data.

### Errors

| Code | Status | When |
|------|--------|------|
| `not_found` | 404 | No group with that id in the calling game (also returned for soft-deleted rows and cross-game ids). |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `GET /v1/groups`

Lists groups for the calling game, newest-first. Cursor-based pagination via the `Page<T>` envelope.

### Query parameters

| Field | Type | Default | Notes |
|-------|------|---------|-------|
| `limit` | int | `50` | 1-100 inclusive. Out-of-range values return `400`. |
| `cursor` | string | none | The `nextCursor` from a prior response. Must point at a group in the calling game; soft-deleted is fine, the cursor row is used purely as a sort position. |
| `gameId` | string | the calling game | Optional. If provided, must equal the calling key's game id; mismatches return `400`. |
| `viewer` | string | none | Optional external user id. When supplied, groups with `visibility = "secret"` are filtered out unless `viewer` is an active member. Omitting `viewer` is treated as a server-to-server / admin call and returns every non-deleted group regardless of visibility. |
| `kind` | string | none | Optional exact-match filter on the group's `kind`. 1-64 characters; longer or empty values return `400`. A kind no group uses is a valid query that returns an empty page, not an error. Matching is exact: neither prefix nor case-insensitive. Composes with `cursor`, `limit`, and `viewer`. |

### Filtering by kind

`name` is unique per game, **not** per kind, so two groups of different kinds can share a name. Finding a group by name alone can therefore pick up the wrong one: a player-named `campaign` called "Skyreach" collides with an `instance` group of the same name. Filter on `kind` server-side, and match on the `(kind, name)` pair when you need find-or-create semantics.

```
GET /v1/groups?kind=instance
GET /v1/groups?kind=campaign&viewer=user_alice&limit=25
```

The filter is backed by the `(gameId, kind)` index, so it stays cheap as the group count grows.

### Response

`200 OK` with a `Page<Group>` body. Items are sorted by `createdAt` desc with `id` desc as a tiebreaker so pagination is deterministic even when many groups share a timestamp. `nextCursor` is `null` when no further pages remain.

```json
{
  "items": [
    {
      "id": "ckxxx...",
      "gameId": "ckyyy...",
      "kind": "guild",
      "name": "Crimson Wolves",
      "visibility": "invite-only",
      "metadata": {},
      "defaultRoleId": null,
      "memberCount": 42,
      "hasPasscode": false,
      "createdAt": "2026-04-28T05:00:00.000Z",
      "updatedAt": "2026-04-28T05:00:00.000Z",
      "softDeletedAt": null
    }
  ],
  "nextCursor": "ckxxx..."
}
```

`memberCount` per item is the count of `GroupMember` rows in `status = "active"`, computed at request time via a single batched `groupBy` query (no N+1).

List items carry no `version`. Read the group with `GET /v1/groups/:id` for a version to send as `If-Match`.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | `limit` invalid, `cursor` not found in this game, `gameId` does not match the calling game, or `kind` is empty or over 64 characters. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `PATCH /v1/groups/:id`

Partially updates a group. The body is a subset of `{ name, visibility, metadata, defaultRoleId, passcode }`; only the fields included are touched. At least one field must be provided. Soft-deleted groups and groups belonging to a different game return `404 not_found` (the route does not leak existence across game boundaries).

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. |

### Request

```json
{
  "name": "Crimson Lions",
  "visibility": "public",
  "metadata": { "motto": "Roar" },
  "defaultRoleId": null
}
```

| Field | Type | Notes |
|-------|------|-------|
| `name` | string | Optional. 1-120 characters. |
| `visibility` | `"public" \| "invite-only" \| "secret"` | Optional. |
| `metadata` | object | Optional. **Replaces the existing metadata wholesale**; not a deep merge. To preserve unrelated keys, read the current value first and merge client-side. |
| `defaultRoleId` | string \| null | Optional. Pass `null` to clear; pass a string to set. |
| `passcode` | string \| null | Optional. Pass a 4-128 char string to set or replace the join passcode; pass `null` to clear it. Omit to leave any existing passcode untouched. See [Passcodes](#passcodes). |
| `actorUserId` | string | Optional. External user id of the person making the change. Recorded as the audit actor and sent as `actorUserId` on the `group.updated` event. It is not a change itself: a body with only `actorUserId` is a `400`. |

An empty body, a body with only `actorUserId`, an unknown visibility value, an empty `name`, or a malformed JSON body all return `400 bad_request`.

### Headers

| Header | Notes |
|--------|-------|
| `If-Match` | Optional. The group's [version](#group-versions), quoted (`"4211"`) or bare (`4211`). A mismatch answers `412 precondition_failed` with the current version in `details.version` and writes nothing. Checked even when the PATCH changes nothing. |

### Response

`200 OK` with the updated `Group` body and its new [version](#group-versions) in `version` and `ETag`. `memberCount` is computed at request time from active members, just like `GET /v1/groups/:id`.

```json
{
  "id": "ckxxx...",
  "gameId": "ckyyy...",
  "kind": "guild",
  "name": "Crimson Lions",
  "visibility": "public",
  "metadata": { "motto": "Roar" },
  "defaultRoleId": null,
  "memberCount": 42,
  "hasPasscode": false,
  "createdAt": "2026-04-28T05:00:00.000Z",
  "updatedAt": "2026-04-28T06:00:00.000Z",
  "softDeletedAt": null,
  "version": "4215"
}
```

### Audit log

Writes one `group.updated` entry **only when at least one field actually changed**. `actorUserId` is the resolved `JunjoUser` id of the body's `actorUserId`, or `null` without one; a passcode change's `group.passcode.set` / `group.passcode.cleared` entry carries the same actor. The payload is a `{ before, after }` pair containing only the changed fields:

```json
{
  "action": "group.updated",
  "groupId": "ckxxx...",
  "targetId": "ckxxx...",
  "actorUserId": null,
  "payload": {
    "before": { "name": "Old Name", "visibility": "invite-only" },
    "after": { "name": "New Name", "visibility": "public" }
  }
}
```

A no-op PATCH (every supplied field already matches the stored value) succeeds with `200 OK`, returns the unchanged group, writes no audit entry and emits no event. The `updatedAt` timestamp and the version are also unchanged in that case. Metadata is treated as changed whenever it is provided, even when the new value is structurally equal to the stored one (deep equality across `jsonb` ordering is not attempted).

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Empty body, a body with only `actorUserId`, invalid field value, malformed JSON, or a malformed `If-Match`. |
| `not_found` | 404 | No group with that id in the calling game (also returned for soft-deleted rows and cross-game ids). |
| `precondition_failed` | 412 | `If-Match` does not match the group's version. `details.version` is the current version. Nothing was written. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `DELETE /v1/groups/:id`

Soft-deletes a group by stamping `softDeletedAt` with the current time. The group disappears from `GET` and `LIST` responses immediately but the row stays in Postgres for 7 days so it can be restored. After 7 days an in-process sweeper hard-deletes the row (and its cascade-related rows). Pass `?hard=true` to bypass the soft-delete grace and remove the row immediately.

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. |

### Query parameters

| Field | Type | Default | Notes |
|-------|------|---------|-------|
| `hard` | `"true" \| "false"` | `"false"` | `"true"` hard-deletes; `"false"` or absence keeps the soft-delete path. Any other value answers `400 bad_request`. |
| `actorUserId` | string | none | Optional external user id of the person deleting the group. Recorded as the audit actor of a soft delete and sent as `actorUserId` on the `group.deleted` event (soft and hard). |

### Headers

| Header | Notes |
|--------|-------|
| `If-Match` | Optional. The group's [version](#group-versions), quoted or bare. Applies to soft and hard deletes. A mismatch answers `412 precondition_failed` with the current version in `details.version` and deletes nothing. |

### Response

- Soft delete on a live group: `200 OK` with the now-soft-deleted `Group` body (`softDeletedAt` populated) and its new [version](#group-versions) in `version` and `ETag`. Writes one `group.deleted` audit entry in the same transaction.
- Soft delete on an already soft-deleted group: `200 OK` with the existing group body and its current version, `softDeletedAt` left at its prior value, **no second audit entry**, no event, no timestamp bump. Idempotent. A stale `If-Match` still answers `412`.
- Hard delete: `204 No Content`. Cascade rules remove related rows, including the group's audit history and its version. No audit entry is written (it would be cascade-deleted anyway).

### Audit log (soft delete only)

| Field | Value |
|-------|-------|
| `action` | `group.deleted` |
| `groupId` | the deleted group id |
| `targetId` | the deleted group id |
| `actorUserId` | the resolved `JunjoUser` id of the `actorUserId` query parameter, or `null` without one |
| `payload` | `{ kind: "soft", softDeletedAt: <iso>, retentionDays: 7 }` |

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | `hard` is not `"true"` / `"false"`, `actorUserId` is empty, or `If-Match` is malformed. |
| `not_found` | 404 | No group with that id in the calling game (cross-game ids also return 404). |
| `precondition_failed` | 412 | `If-Match` does not match the group's version. `details.version` is the current version. Nothing was deleted. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `POST /v1/groups/:id/restore`

Clears `softDeletedAt` on a group that is still inside the 7-day undo window. Idempotent on a live group; returns `410 Gone` if the soft-delete is older than 7 days (the row may be on the next sweep tick or already gone).

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. |

### Response

- Restore inside the window: `200 OK` with the restored `Group` body (`softDeletedAt: null`) and its new [version](#group-versions) in `version` and `ETag`. Writes one `group.restored` audit entry and emits `group.updated` with `actorUserId: null`.
- Restore on a live (not soft-deleted) group: `200 OK` with the existing group body, no audit entry. Idempotent. This answer carries no `version` or `ETag`; read the group for its version.

Restore does not take `If-Match`.

### Audit log (restore inside window only)

| Field | Value |
|-------|-------|
| `action` | `group.restored` |
| `groupId` | the restored group id |
| `targetId` | the restored group id |
| `actorUserId` | `null` |
| `payload` | `{ previousSoftDeletedAt: <iso> }` |

### Errors

| Code | Status | When |
|------|--------|------|
| `restore_window_expired` | 410 | The group's `softDeletedAt` is older than 7 days. The row may be hard-deleted soon (or already). |
| `not_found` | 404 | No group with that id in the calling game (cross-game ids also return 404). Hard-deleted rows return 404 because the row is gone. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

### Background sweeper

Soft-deleted groups whose `softDeletedAt` is older than `SOFT_DELETE_RETENTION_DAYS` (7) are removed by an in-process scheduler running on `setInterval` inside the same Node process as the API. The interval defaults to one hour. There is no separate worker process or external cron. Keeping background work in-process avoids an operational dependency for self-hosters.

## `POST /v1/groups/:id/invitations`

Creates an invitation. Two variants share the same endpoint, picked by whether `targetUserId` is present in the body:

- **Direct invite** (`targetUserId` set): a single-use invitation addressed to a specific external user id (the one returned by the configured auth adapter).
- **Open code** (`targetUserId` omitted): an invitation anyone with the code can accept. Pair with `expiresIn` to make it a short-lived link.

The server picks a unique 16-character hex code in both cases; subsequent endpoints (`GET /v1/invitations/:code`, accept/decline) read invitations by that code.

Soft-deleted groups and groups belonging to a different game return `404 not_found` (existence is not leaked across game boundaries).

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. |

### Request

```json
{
  "targetUserId": "user_alice",
  "roleId": "role_officer",
  "expiresIn": "7d"
}
```

| Field | Required | Notes |
|-------|----------|-------|
| `targetUserId` | no | Omit for an open-code invitation. When set, this is the external user id from the dev's auth provider; stored verbatim, the server does not require a corresponding `JunjoUser` row at invite time. |
| `roleId` | no | A role hint stored on the invitation. Not auto-applied at acceptance time today (call [`members.assignRole`](/sdk/members#assignrolegroupid-userid-roleid-opts) afterward) and not validated against the group's roles. |
| `expiresIn` | no | Duration string `<positive integer><unit>` where unit is `s`, `m`, `h`, or `d`. Examples: `30s`, `15m`, `2h`, `7d`. The server stamps `expiresAt = now() + expiresIn` at create time. |

An empty `targetUserId`, a malformed `expiresIn`, an `expiresIn` with a non-positive value (e.g., `0d`), or a malformed JSON body all return `400 bad_request`.

### Response

`201 Created` with an `Invitation` body. Timestamps are ISO 8601 strings.

```json
{
  "id": "ckxxx...",
  "groupId": "ckyyy...",
  "code": "abcd1234abcd1234",
  "roleId": "role_officer",
  "targetUserId": "user_alice",
  "createdBy": null,
  "createdAt": "2026-04-28T05:00:00.000Z",
  "expiresAt": "2026-05-05T05:00:00.000Z",
  "usedAt": null,
  "usedBy": null
}
```

For an open-code invitation the response is the same shape with `"targetUserId": null`.

`createdBy` is `null` because no auth-adapter actor is wired through this code path. The field parallels `AuditEntry.actorUserId`.

### Audit log

Every successful create writes one entry:

| Field | Value |
|-------|-------|
| `action` | `member.invited` |
| `groupId` | the group id |
| `targetId` | the invited `targetUserId`, or `null` for open-code invitations |
| `actorUserId` | `null` |
| `payload` | `{ invitationId, code, targetUserId, roleId, expiresAt }` (each value is `null` when not set on the invitation) |

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Body fails validation, malformed JSON, malformed or non-positive `expiresIn`. |
| `not_found` | 404 | No group with that id in the calling game (also for soft-deleted rows and cross-game ids). |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `GET /v1/groups/:id/invitations`

Lists invitations for a group, scoped to the calling game. Soft-deleted groups and groups belonging to a different game return `404 not_found`. Cursor-based pagination via the `Page<T>` envelope.

By default the response excludes invitations that have already been used (`usedAt` set) or have expired (`expiresAt < now()`). Pass `includeUsed=true` and/or `includeExpired=true` to include them.

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. |

### Query parameters

| Field | Type | Default | Notes |
|-------|------|---------|-------|
| `limit` | int | `50` | 1-100 inclusive. Out-of-range values return `400`. |
| `cursor` | string | none | The `nextCursor` from a prior response. Must point at an invitation in this group. |
| `includeExpired` | `"true" \| "false"` | `false` | When `true`, expired invitations are included. |
| `includeUsed` | `"true" \| "false"` | `false` | When `true`, used invitations (with `usedAt` set) are included. |

### Response

`200 OK` with a `Page<Invitation>` body. Items are sorted by `createdAt` desc with `id` desc as a tiebreaker. `nextCursor` is `null` when no further pages remain.

```json
{
  "items": [
    {
      "id": "ckxxx...",
      "groupId": "ckyyy...",
      "code": "abcd1234abcd1234",
      "roleId": null,
      "targetUserId": "user_alice",
      "createdBy": null,
      "createdAt": "2026-04-28T05:00:00.000Z",
      "expiresAt": null,
      "usedAt": null,
      "usedBy": null
    }
  ],
  "nextCursor": null
}
```

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | `limit` invalid, `cursor` not in this group, `includeExpired`/`includeUsed` not `"true"`/`"false"`. |
| `not_found` | 404 | No group with that id in the calling game (also for soft-deleted rows and cross-game ids). |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## Group versions

Every group carries a `version`: the [stream position](/api-reference/events#positions) of the latest logged event about the group. That covers:

- the group's own events (`group.updated`, `group.deleted`);
- the events of its members, roles, permissions, overrides and invitations;
- `group.relationship.changed` where the group is the A side (`groupId`). Setting A's stance toward B moves A's version, not B's.

A group no logged event has touched yet is at version `"0"`. A write that changes nothing emits no event and leaves the version as it is.

The version is a decimal string that can exceed 2^53, like a position. It only increases, but not by one per write: positions are shared by every event of the game. Treat it as opaque and compare it for equality.

Single-group responses carry it as `version` in the body and in the `ETag` header: `GET /v1/groups/:id`, `POST /v1/groups` (201), `PATCH /v1/groups/:id`, soft `DELETE /v1/groups/:id` (200) and `POST /v1/groups/:id/restore`. `GET /v1/groups` items and the `group` inside `group.updated` leave it out. Export `group` records carry it too ([Export](/api-reference/export#record-kinds)).

```
ETag: "4211"
```

`PATCH /v1/groups/:id` and `DELETE /v1/groups/:id` (soft and `?hard=true`) accept `If-Match` with that version:

- Quoted (`If-Match: "4211"`) or bare (`If-Match: 4211`), up to 19 digits. Any other value answers `400 bad_request`.
- A mismatch answers `412 precondition_failed` with the current version in `details.version`, and nothing is written.
- The check also applies to a PATCH that changes nothing, so a stale queued edit is reported instead of silently succeeding.

```json
{
  "code": "precondition_failed",
  "status": 412,
  "message": "If-Match \"4198\" does not match group ckxxx...'s version (current \"4211\")",
  "details": { "version": "4211" }
}
```

The check runs when the write's events are logged, while the game's event counter is locked, so it sees every other write in the game that committed first. Of several writers that send the same `If-Match` and each change the group, exactly one succeeds and the others get `412`.

On the [game stream](/api-reference/events#get-v1events), the position of an event about a group is the version that event gave the group. A stream consumer can therefore track a group's version from the events alone. A hard delete removes the group's version with the group.

The group version is separate from [member versions](#member-versions). A member write moves both, and member-scoped writes (including kick) still take the member version in `If-Match`.

## Member versions

Every membership carries a `version`: 1 when the row is created, and one higher after every write that changes it. Joins, adds, invitation accepts, imports, leaves, kicks, group bans and unbans, role assigns and unassigns, override sets and clears, metadata and notes edits, and identity merges that move a membership to another person all count, including the same writes from the dashboard. A write that changes nothing (a repeated assign, a kick of someone already gone) leaves the version alone, and so do role-level edits such as changing a role's entries, parents or name.

The version is on every `Member` object (including the `member` inside `member.joined`), on `GET /v1/groups/:id/members/:userId/access`, and in the `ETag` header of single-member reads and member-scoped write responses:

```
ETag: "4"
```

Member-scoped writes accept `If-Match` with that version (quoted, or a bare integer): `PATCH /v1/groups/:id/members/:userId`, role assign and unassign, override set and clear, kick, and group ban and unban. The check runs inside the write's transaction. A mismatch answers `412 precondition_failed` and writes nothing, a malformed value answers `400 bad_request`, and a missing member answers `404`. The check also applies when the write would be a no-op, so a stale queued write is reported instead of silently succeeding.

`POST /v1/groups/:id/members` takes the opposite precondition, `If-None-Match: *`, which makes the add create-only (see [Create-only adds](#create-only-adds)).

Member events carry `memberVersion`, the version after the write (see [Events](/api-reference/events#versions-on-events)). See [Safe retries for queued writes](/api-reference#safe-retries-for-queued-writes) for pairing `If-Match` with `Idempotency-Key`.

## `POST /v1/groups/:id/members`

Adds a user to a group directly. This is the server-to-server counterpart to `join`: it **ignores `visibility`**, so an `invite-only` or `secret` group can be populated without making it publicly joinable and without running the two-call invitation handshake.

Use it for provisioning: backfilling groups from an existing application database, seeding internal authorization groups, or any flow where your backend has already decided the user belongs.

The `jk_` key is already admin-class (see [Security model](/security-model)), so a caller holding it could create an invitation and accept it on the user's behalf anyway. Gating this path on discoverability would add steps without adding a boundary, so it does not. Bans are a different matter and **are** still enforced: a ban is state your game set deliberately, and silently overriding it during a bulk provision would be wrong.

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. Must belong to the calling game and not be soft-deleted. |

### Body

| Field | Required | Notes |
|-------|----------|-------|
| `userId` | yes | The dev's external user id. Its `JunjoUser` and `ExternalIdentity` are created on demand, so the user does not have to exist in Junjo yet. |
| `roleId` | no | Assigned in the same transaction as the membership. Must belong to this group. Saves the join-then-assign two-step and cannot leave a member role-less if a second call fails. |
| `actorUserId` | no | External user id of the acting moderator, recorded on the audit entries. |

Unknown fields are rejected with `400`.

```json
{ "userId": "user_alice", "roleId": "role_officer" }
```

### Response

The `Member` row, with a status code that reports whether the call changed anything:

| Status | When |
|--------|------|
| `201 Created` | The call made the user an active member: a new row, or a reactivation from `left` / `kicked` (which keeps the original `joinedAt`). |
| `200 OK` | The user was already an active member. Nothing changed, except that a supplied `roleId` they did not hold is still assigned. |

That split makes the route idempotent while still letting a provisioning script report how many members it actually added on a re-run. The response carries the member's version as `ETag`; one call raises the version by one at most (a new member starts at 1 even when `roleId` is assigned in the same call).

Concurrent identical adds resolve themselves: the loser's transaction rolls back and retries, and the retry takes the already-active path. The rollback drops its staged events and audit rows with it, so a race cannot double-emit `member.joined`.

### Create-only adds

By default the route merges into whatever membership already exists: an active member who lacks `roleId` gains it, and a `left` or `kicked` row is reactivated. A caller that wants to store a person with a starting role, but never change anyone who is already there, cannot get that safely with a read followed by an add: a promotion that lands in between leaves the member holding both roles.

Send `If-None-Match: *` to make the add create-only:

```
POST /v1/groups/grp_123/members
If-None-Match: *
Content-Type: application/json

{ "userId": "user_alice", "roleId": "role_member" }
```

- When the person has **no membership row** in the group, the add runs exactly as without the header: `201 Created`, the same body, events and audit entries.
- When a row exists **in any status** (`active`, `left`, `kicked`, `invited` or `banned`, including one held under another of the person's [linked ids](/api-reference/identity#person-and-linked-ids)), the server writes nothing (no row change, role, event or audit entry) and answers `412 precondition_failed`. The message names the row's status, `details.memberStatus` carries it, and the `ETag` header carries the existing member's version.
- Any other `If-None-Match` value, such as an entity tag or a list, answers `400 bad_request` before anything is read or written.

```json
{
  "code": "precondition_failed",
  "status": 412,
  "message": "If-None-Match * failed: the user already has a membership row in this group with status active",
  "details": { "memberStatus": "active" }
}
```

The check runs inside the add's transaction, under the same group lock as the write, so two concurrent create-only adds of one person produce exactly one `201` and one `412`, and a concurrent join or add of the same person is never overwritten.

Every other refusal is answered first, as it would be without the header: a malformed body, an unknown group or role, a role from another group, and a ban (`403 banned`, including an active group ban whose row exists). The `412` therefore always means that the row exists and the request was otherwise acceptable. A group ban that has expired no longer blocks the add, so its `banned` row answers `412`. [Kind limits](#kind-limits) are not evaluated when the answer is `412`.

With `Idempotency-Key`, a retry of a create-only add replays the first answer: the `201` that created the member, not a `412` caused by its own earlier success.

### Events and audit

Fired only on an actual transition, so a re-run is silent:

- becoming active writes a `member.joined` audit entry with `via: "admin-add"` and emits `member.joined`;
- a newly assigned `roleId` writes a `role.assigned` audit entry and emits `role.changed`.

Any new role is reported by `role.changed`, so the event stream reads like the join-then-assign sequence this route replaces. Both events carry one `memberVersion` ([versions on events](/api-reference/events#versions-on-events)), and the `member` inside `member.joined` already lists the new role.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | `userId` missing or empty, an unknown field was sent, or `If-None-Match` is present with a value other than `*`. |
| `precondition_failed` | 412 | `If-None-Match: *` was sent and the person already has a membership row in this group, in any status. Nothing was written. See [Create-only adds](#create-only-adds). |
| `role_group_mismatch` | 400 | `roleId` exists but belongs to another group. No member is created. |
| `not_found` | 404 | The group, or a supplied `roleId`, does not exist in the calling game. No member is created. |
| `banned` | 403 | The user is banned game-wide or from this group. An expired timed ban does not block the add. |
| `group_full` | 409 | Adding the user would exceed the kind's `maxMembers` ([Kind limits](#kind-limits)). |
| `group_limit_reached` | 409 | The user already holds the kind's `maxPerUser` active memberships. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `POST /v1/groups/:id/members/import`

Imports up to 500 memberships in one call, with their roles, overrides and metadata. Built for moving an existing permission setup into Junjo: like `POST /v1/groups/:id/members` it ignores `visibility`, and it runs in one transaction, so either every row applies or none does.

### Body

```json
{
  "members": [
    {
      "userId": "mc:0f8fad5b-d9cb-469f-a165-70867728950e",
      "roleIds": ["role_a", "role_b"],
      "overrides": [
        { "permission": "fly", "value": true },
        { "permission": "fly", "value": false, "context": { "world": "spawn" } }
      ],
      "metadata": { "prefix": "[VIP]" }
    }
  ],
  "allowBanned": false,
  "actorUserId": "web:mod_jane"
}
```

| Field | Required | Notes |
|-------|----------|-------|
| `members` | yes | 1 to 500 rows. Each `userId` may appear once, and two linked ids of the same person may not both appear. |
| `members[].userId` | yes | The dev's external user id. Unknown users are created. |
| `members[].roleIds` | no | Replaces the member's roles. Every id must be a role of this group. `[]` removes all roles. |
| `members[].overrides` | no | Replaces the member's overrides, global and contextual, in the role-entry shape `{ permission, value, context? }`. `context` limits an override to a [context](/api-reference/permissions#contexts); absent or `{}` is global. Each `(permission, context)` pair may appear once per row. `[]` clears them all. Keys follow the game's [permission mode](/api-reference/permissions#permission-modes), and context values are folded in both modes. |
| `members[].metadata` | no | Replaces the member's metadata. |
| `allowBanned` | no | `true` imports banned people without changing any ban. Default `false`. |
| `actorUserId` | no | External user id of the acting moderator, recorded on the audit entries and on `role.changed`. |

Each row ensures an active membership: a new member is created, and a `left`, `kicked` or `invited` row is reactivated. A field that is present replaces the current value; a field that is absent is left as it is. Like `POST /v1/groups/:id/members`, join and invitation accept, the import never assigns the group's `defaultRoleId`. A created member holds the roles in `roleIds` (none when it is omitted), and a reactivated member keeps the roles it already had unless `roleIds` is sent.

Bans: a person banned from the game or from this group fails their row with `banned`. With `allowBanned: true` their roles, entries and metadata are imported and no ban changes: a group-banned member keeps status `banned`, and a game-banned person becomes (or stays) an active member while the game ban still applies.

### Validation

Every row is checked before anything is written. If any row fails, nothing is written and the call answers `400 bad_request`, or, when every failing row has the same one of these codes, `403 banned`, `409 group_full` or `409 group_limit_reached`. `details.rows` lists every failing row:

```json
{
  "code": "bad_request",
  "status": 400,
  "message": "2 of 120 rows failed; see details.rows",
  "details": {
    "rows": [
      { "index": 3, "userId": "mc:not-a-uuid", "code": "invalid_user_id", "message": "userId does not match its namespace's declared format" },
      { "index": 7, "userId": "mc:7c9e6679-7425-40de-944b-e07fc1f90ae7", "code": "banned", "message": "user is banned from this game" }
    ]
  }
}
```

| Row code | When |
|----------|------|
| `bad_request` | The row is malformed, repeats an earlier `userId` or person, names a role of another group, has an invalid permission key or context, or repeats a `(permission, context)` pair. |
| `invalid_user_id` | `userId` breaks its namespace's [declared format](/api-reference/identity#canonical-formats). |
| `not_found` | A `roleIds` entry names no role. |
| `banned` | The person is banned from the game or the group and `allowBanned` is not set. |
| `group_full` | The row would make someone an active member beyond the kind's `maxMembers`. Rows are admitted in order, so the rows past the remaining room fail. |
| `group_limit_reached` | The person already holds the kind's `maxPerUser` active memberships in other groups. |

Only rows that would make someone active (new members and reactivations) count against [kind limits](#kind-limits); rows for existing active members and for group-banned people kept banned do not.

`index` is the row's position in `members`, from 0.

### Response

`200 OK`:

```json
{
  "created": 1,
  "reactivated": 0,
  "updated": 3,
  "unchanged": 116,
  "items": [{ "userId": "mc:0f8fad5b-d9cb-469f-a165-70867728950e", "status": "created", "version": 1 }]
}
```

`items` follows the order of `members`. `status` is `created`, `reactivated`, `updated` (an existing member whose roles, entries or metadata changed) or `unchanged`. `version` is the member's version after the call; it rises by one for each member the call changed, however many of their fields changed. Running the same import again reports every row `unchanged` and writes nothing, so a failed import can be retried.

### Events and audit

The same events and audit entries the equivalent single calls produce, staged in the import's transaction:

- `member.joined` (audit `via: "import"`) for each created or reactivated member;
- `role.changed` with the roles added and removed, and `role.assigned` / `role.unassigned` audit entries;
- `member.updated` with `changed` listing `metadata` and / or `overrides`, and `member.metadata.updated`, `permission.override.set` and `permission.override.cleared` audit entries.

The events for one member carry one `memberVersion` ([versions on events](/api-reference/events#versions-on-events)), and the `member` inside `member.joined` is the member as the import leaves it (final roles and metadata). Unchanged members produce nothing.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | `members` is missing, empty or longer than 500 rows, an unknown top-level field was sent, or a row failed (see `details.rows`). |
| `banned` | 403 | Every failing row is a ban (see `details.rows`). |
| `group_full` | 409 | Every failing row is `group_full`. |
| `group_limit_reached` | 409 | Every failing row is `group_limit_reached`. |
| `not_found` | 404 | No group with that id in the calling game. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `POST /v1/groups/:id/join`

Open join for a group whose `visibility` is `"public"`. Use this when the dev wants users to be able to add themselves to a group without an `Invitation`. Invite-only and secret groups still go through the invitation flow; this route returns `403` (invite-only) or `404` (secret) for them.

If the user previously left or was kicked from this group, the existing `GroupMember` row is reactivated rather than duplicated; `joinedAt` is preserved, `leftAt` is cleared, and `status` flips back to `"active"`.

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The group id. |

### Request

```json
{ "userId": "user_alice", "passcode": "open-sesame" }
```

| Field | Required | Notes |
|-------|----------|-------|
| `userId` | yes | The dev's external user id. The route auto-creates a `JunjoUser` and `ExternalIdentity` for unknown users (same upsert semantics as invitation accept). |
| `passcode` | conditional | Required when the target group has `hasPasscode: true`; ignored otherwise. The passcode check runs **before** identity resolution so a wrong passcode does not auto-create a `JunjoUser` for the caller's id. |

### Response

`201 Created` with the `Member` body, identical in shape to the invitation-accept response.

```json
{
  "id": "ckxxx...",
  "groupId": "ckyyy...",
  "userId": "user_alice",
  "status": "active",
  "roles": [],
  "metadata": {},
  "notesPublic": null,
  "notesPrivate": null,
  "joinedAt": "2026-04-28T05:00:00.000Z"
}
```

### Audit log

Writes one `member.joined` entry per successful join. The payload carries `via: "public-join"` so audit consumers can distinguish open joins from invitation redemptions.

| Field | Value |
|-------|-------|
| `action` | `member.joined` |
| `groupId` | the group id |
| `targetId` | the joiner's external user id |
| `actorUserId` | the joiner's resolved JunjoUser id |
| `payload` | `{ memberId, via: "public-join" }` |

### Webhook event

Fires `member.joined` with the new `Member` body, mirroring the invitation-accept flow.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Body missing `userId` or malformed JSON. |
| `permission_denied` | 403 | The group's `visibility` is `"invite-only"`. The error message is `"this group requires an invitation to join"`. |
| `passcode_required` | 403 | The group has a passcode set and the body omitted `passcode`. |
| `passcode_invalid` | 403 | The supplied `passcode` did not match. |
| `banned` | 403 | The user is game-banned or per-group-banned (with an active `bannedUntil`). |
| `not_found` | 404 | No group with that id in the calling game, or the group is soft-deleted, or the group's `visibility` is `"secret"` (existence stays invisible to non-members). |
| `already_member` | 409 | The user already has an active `GroupMember` row in this group. Also the losing outcome when two concurrent joins for the same user race: the winner gets 201, the loser gets this 409. If the goal is "make sure the user is a member", treat it as success. |
| `group_full` | 409 | The group is at its kind's `maxMembers` ([Kind limits](#kind-limits)). |
| `group_limit_reached` | 409 | The user already holds the kind's `maxPerUser` active memberships. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `POST /v1/groups/:id/members/:userId/kick`

Removes a member from a group on the dev backend's behalf. Only an `active` member is transitioned to `kicked`; any other state is returned unchanged with no audit entry, so a second kick (or a kick on a left member) is idempotent.

### Path parameters

## Per-group bans

Distinct from kick: a kicked member can rejoin via the public-join or
invitation-accept flow; a banned member cannot. Per-group bans live as
`GroupMember.status = "banned"` with optional `bannedUntil` (lazy
expiry: read paths treat an expired value as not-banned).

For game bans that apply across every group in the game, see the
[Bans reference](/api-reference/bans).

### `POST /v1/groups/:id/members/:userId/ban`

**Body**

```json
{
  "reason": "trolling",
  "expiresAt": "2026-06-01T00:00:00.000Z"
}
```

Both fields optional; omit / `null` for a permanent ban with no
recorded reason. The handler auto-creates a `JunjoUser` +
`ExternalIdentity` if the user has never been seen, so a moderator can
preemptively ban a user who hasn't joined.

Writes a `member.banned` audit entry with `{ memberId, reason, bannedUntil }`
and fires the `member.banned` webhook event with `{ userId, reason, bannedUntil }`.

**Response** `200 OK` with the post-state `Member` body and its version

`POST /v1/groups/:id/join` and `POST /v1/invitations/:code/accept`

## Passcodes

Optional shared-secret join gate, set per-group. When a group has a
passcode, `POST /v1/groups/:id/join` requires the caller to send a
matching `passcode` field in the body in addition to passing the
visibility / ban checks. Stored as a scrypt hash (same primitive as
API keys); the plaintext is never returned by any route. Surfaced in
serialized `Group` responses as `hasPasscode: boolean`.

Passcode is **orthogonal to visibility**: it is not a fourth visibility
mode. A `"public"` group with a passcode is "discoverable but gated"
(the listening-room pattern). An `"invite-only"` or `"secret"` group
with a passcode is harmless: the `/join` route is already blocked, and
invitation accept does not consult the passcode (the invitation IS
the credential).

### Setting a passcode

| Surface | Behavior |
|---------|----------|
| `POST /v1/groups` | Optional `passcode: string` (4-128 chars). |
| `PATCH /v1/groups/:id` | Optional `passcode: string \| null`. String sets/replaces; `null` clears; omit to leave existing untouched. |

### Verification

`POST /v1/groups/:id/join` runs the passcode check **before** identity
resolution, so a wrong passcode does not auto-create a `JunjoUser` for
the caller's id (no enumeration via failed attempts).

| Code | Status | When |
|------|--------|------|
| `passcode_required` | 403 | Group has a passcode set but the body omitted `passcode`. |
| `passcode_invalid` | 403 | Supplied `passcode` did not match. |

### Audit

Passcode transitions write a dedicated audit row in addition to the
standard `group.updated` row. Plaintext is never logged; only the
transition shape:

| Action | Payload | When |
|--------|---------|------|
| `group.passcode.set` | `{ transition: "set" }` | First time a passcode is set on this group. |
| `group.passcode.set` | `{ transition: "rotated" }` | A new passcode replaces an existing one. |
| `group.passcode.cleared` | `{ transition: "cleared" }` | Existing passcode is removed (`passcode: null`). |

Filter via `?actions=group.passcode.set,group.passcode.cleared` on
the `/admin/audit` endpoint to see every passcode change for a game
without scanning `group.updated` payloads.

### Rate limiting

Two in-process token buckets fire **before** scrypt verify, so a
brute-forcer cannot burn server CPU:

| Bucket | Cap | Purpose |
|--------|-----|---------|
| per-(group, userId) | 5 attempts/minute, burst 5 | Bounds a single user's attempt rate against one group. |
| per-group | 30 attempts/minute, burst 30 | Bounds total fanout across rotating userIds (the per-user bucket alone wouldn't catch a userId-rotating attacker). |

Either limit being exhausted returns `429 rate_limit_exceeded` with a
`Retry-After` header. Buckets are per-process (not shared across
horizontally-scaled instances); a multi-process deployment gets
proportionally higher effective ceilings.

### PINs

A "PIN" is just a numeric passcode. The 4-128 character bound on
`passcode` accepts `"1234"`, `"00000"`, etc., so consumers wanting a
keypad UX can pass digits straight through `groups.join({ passcode:
"1234" })`. There is no separate PIN concept on the Junjo side: the
audit, rate-limiting, and storage all funnel through the single
passcode primitive.

## `POST /v1/groups/:id/bulk-invite`

Creates many open-code invitations at once. Body is plain text: one trimmed, non-empty line per target external user id.

```http
POST /v1/groups/:id/bulk-invite[?roleId=<RoleId>]
Authorization: Bearer <api-key>
Content-Type: text/csv

user_alice
user_bob
user_carol
```

### Path params

| Param | Type | Notes |
|-------|------|-------|
| `id` | `GroupId` | The group to invite into. URL-decoded. |

### Query params

| Param | Required | Notes |
|-------|----------|-------|
| `roleId` | no | Forwarded to every created invitation as `Invitation.roleId`. |

### Body format

- One userId per line. Leading and trailing whitespace are trimmed.
- Empty lines (or lines that are whitespace only) are silently skipped and do not appear in any count.
- Each non-empty line is treated as a single CSV field; commas are not parsed as separators.
- Both `\n` and `\r\n` line endings are accepted.
- Userids longer than 255 characters are reported in `errors` (the row is not invited, not skipped).
- Userids that break a [declared id format](/api-reference/identity#canonical-formats) are reported in `errors` the same way, instead of failing the request with `400 invalid_user_id`.
- The total row count (errored + valid) is capped at 1000 per request; exceeding returns `400 bad_request`.

### Response

```json
{
  "invited": 47,
  "skipped": 3,
  "errors": [
    { "row": 5, "reason": "userId exceeds 255 characters" }
  ]
}
```

| Field | Type | Notes |
|-------|------|-------|
| `invited` | number | Count of new `Invitation` rows created. |
| `skipped` | number | Count of rows that were not invited because the user is already an active member, or already has an unused, unexpired invitation, or appeared earlier in the same batch. |
| `errors` | array | One entry per malformed row. `row` is 1-indexed and counts every source line (empty lines included), so the dev can map errors back to the original input. |

### Audit log

One `member.invited` audit entry is written per created invitation, all in the same transaction. `actorUserId` is `null`; `targetId` is the invited user's external id; `payload.source` is the string `"bulk-invite"` so audit consumers can distinguish bulk-issued invitations from single-shot `inviteByUserId` ones.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | More than 1000 rows in one request, or `roleId=` empty. |
| `not_found` | 404 | No group with that id in the calling game (soft-deleted and cross-game collapse here). |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

`setBy` is a user id rendered with the caller's [namespace preference](/api-reference/identity#preferred-namespaces), like other user ids, on this response and on the relationship reads below. Writes made from the dashboard set it to `null`.

### Behavior

- Each direction is independent. If A->B already has the supplied `type`, that direction is a no-op (no DB write, no audit entry, no `since` bump, and the existing `setBy` is kept). The other direction (B->A) still goes through its own check.
- A direction whose `type` actually changes writes one `group.relationship.set` audit entry on the *origin* group's audit log, with the resolved `JunjoUser` id of `actorUserId` as its actor (or `null`). Mutual writes therefore produce up to two audit entries; partial-mutual writes produce one.
- Self-relationships (`a === b`) are rejected with `400 bad_request`.
- The audit payload is `{ groupAId, groupBId, type, mutual, before? }`. `before` is included only when the row already existed and the type changed; on a fresh insert `before` is omitted.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Body missing `type`, `type` empty or over 64 chars, an empty `actorUserId`, body malformed JSON, or `a === b`. |
| `not_found` | 404 | Either group does not exist, is soft-deleted, or belongs to a different game. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `DELETE /v1/groups/:a/relationships/:b`

Clear the directed A->B relationship. Idempotent: a missing row is a no-op (no audit entry). Pass `?mutual=true` to clear B->A in the same transaction.

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `a` | string | The origin group id. URL-decoded. |
| `b` | string | The target group id. URL-decoded. |

### Query parameters

| Field | Type | Notes |
|-------|------|-------|
| `mutual` | `"true"` \| `"false"` | Optional. When `"true"`, clears both A->B and B->A. Strict string match. |
| `actorUserId` | string | Optional. External user id of the person clearing the relationship. Recorded as the audit actor and sent as `actorUserId` on the `group.relationship.changed` event. |

### Response

`204 No Content`. The audit log carries the previous `type` for any direction that was actually deleted.

### Behavior

- For each direction (A->B, plus B->A when `mutual=true`):
  - If no row exists: no-op for that direction.
  - If a row exists: hard-deleted, and one `group.relationship.cleared` audit entry is written on the *origin* group's audit log with `payload: { groupAId, groupBId, type, mutual }` (where `type` is the row's previous value) and the resolved `JunjoUser` id of `actorUserId` as its actor (or `null`).
- Self-relationships (`a === b`) are rejected with `400 bad_request`.

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | `mutual` is not `"true"` / `"false"`, `actorUserId` is empty, or `a === b`. |
| `not_found` | 404 | Either group does not exist, is soft-deleted, or belongs to a different game. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `PUT /v1/groups/:id/parent`

Set or clear the sub-group / alliance parent. The parent must be in the same game and not soft-deleted. Cycle detection: a candidate that would create a loop in the parent chain is rejected with `400 parent_cycle`.

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The child group id. URL-decoded. |

### Request body

| Field | Type | Notes |
|-------|------|-------|
| `parentGroupId` | string \| null | Required. Set to a group id to nest under that parent; set to `null` to clear the parent. Omitting the field returns `400 bad_request`. |

### Response

`200 OK` with the updated `Group` (the child). `parentGroupId` reflects the new value.

### Behavior

- A child group with `parentGroupId` already equal to the supplied value is a no-op (no DB write, no audit entry); the unchanged group is returned.
- The candidate parent's ancestor chain is walked; if the child group itself appears anywhere in that chain (including the candidate being the child's own id), the call is rejected with `400 parent_cycle`. The walk is bounded at depth 100 to defend against corrupted state.
- On a value change, one audit entry is written on the *child* group's audit log:
  - `group.parent.set` when the new value is non-null.
  - `group.parent.cleared` when the new value is null.
- The audit `payload` is `{ before, after }` carrying the prior and new parent ids (either may be null). The audit row's `targetId` is the new parent id (null when cleared). `actorUserId` is null (no auth-adapter actor wired).

### Errors

| Code | Status | When |
|------|--------|------|
| `bad_request` | 400 | Body missing `parentGroupId`, value is not a non-empty string or null, or body is malformed JSON. |
| `parent_cycle` | 400 | `parentGroupId === id`, or the candidate is already a descendant of the child. |
| `not_found` | 404 | The child or candidate parent does not exist, is soft-deleted, or belongs to a different game. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |

## `GET /v1/groups/:id/children`

List the direct children of a group (groups whose `parentGroupId` points at this one).

### Path parameters

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | The parent group id. URL-decoded. |

### Response

`200 OK` with a bare `Group[]` body, sorted by `createdAt desc, id desc` to match `groups.list`. Soft-deleted children are excluded. Each item carries a fresh `memberCount`.

```json
[
  { "id": "grp_child_2", "name": "Second", "parentGroupId": "grp_parent", "memberCount": 0, "...": "..." },
  { "id": "grp_child_1", "name": "First", "parentGroupId": "grp_parent", "memberCount": 3, "...": "..." }
]
```

A group with no live direct children returns `[]`. Grandchildren are not included; call `listChildren` on each child for a multi-level tree.

### Errors

| Code | Status | When |
|------|--------|------|
| `not_found` | 404 | Parent group does not exist, is soft-deleted, or belongs to a different game. |
| `invalid_api_key` | 401 | API key missing, malformed, or revoked. |
