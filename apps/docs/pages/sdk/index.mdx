# SDK overview

`@junjo.io/sdk` is the TypeScript client. Same package runs in Node and the browser; tree-shakeable; one runtime dependency, `@junjo.io/shared` (the shared type package). Networking uses the built-in `fetch`. The `@junjo.io/sdk/adapters` entry bundles `jose` internally for JWT verification, so the adapters add no install-time dependency either.

## Construct a client

```ts
import { Junjo } from "@junjo.io/sdk";

const junjo = new Junjo({
  apiKey: process.env.JUNJO_API_KEY!,
  // baseUrl: "https://api.junjo.io", // default
});
```

This example targets a server. The `jk_` key is a full-control secret; never expose it to browsers via `NEXT_PUBLIC_` / `VITE_` style env vars. Browser apps construct with `proxy: true` and let a backend proxy inject the key; see [JunjoProvider + useJunjo](/react/provider#browser-apps-proxy-mode).

| Option | Required | Notes |
|--------|----------|-------|
| `apiKey` | yes, unless `proxy` | The full `prefix.secret` string. Hosted-beta keys arrive by email (there is no beta dashboard login yet); self-host and local dev issue one via `npm run db:seed`. Server-side only. |
| `proxy` | no | Browser mode: requests go to `baseUrl` (required) with no `authorization` header; passing `apiKey` throws `invalid_config`. Your backend forwards to the Junjo API and injects the key. |
| `baseUrl` | no | Override the API root. Trailing slashes are stripped. Defaults to the cloud endpoint. Required in proxy mode (point it at your proxy route, e.g. `"/api/junjo"`). |
| `inviteBaseUrl` | no | Base URL for the share links built by `groups.inviteByLink` (`${inviteBaseUrl}/invite/${code}`). There is no default: the API origin serves no invite pages, so without this option `inviteByLink` throws `JunjoError` code `invalid_config` (`inviteByCode` / `inviteByUserId` are unaffected). |
| `authAdapter` | no | An `AuthAdapter` (Clerk, Supabase, JWT, or BYO). Used by `verifyToken`; not required for server-to-server calls. |
| `fetch` | no | Override the `fetch` implementation. Useful in environments without a global `fetch`, and to mock requests in tests. |
| `timeoutMs` | no | Per-request timeout in milliseconds; a request that exceeds it rejects with `JunjoError` code `timeout`. Defaults to `30000`. Set `0` to disable. SSE subscriptions are exempt: an event stream stays open by design. Every request-making method also accepts a per-request `timeoutMs` in its options that overrides this client-level value for that call. |

Every request-making method also accepts an `AbortSignal` via `signal` in its options for caller-side cancellation (rejects with code `cancelled`). The SDK never retries automatically; see the [errors reference](/api-reference/errors) for the retry stance and `retryAfterSeconds`.

## Errors

Every method that talks to the server throws `JunjoError` for any non-2xx response. The instance preserves the server's envelope:

```ts
import { JunjoError } from "@junjo.io/sdk";

try {
  await junjo.groups.create({ kind: "guild", name: "" });
} catch (e) {
  if (e instanceof JunjoError) {
    e.code;    // "bad_request"
    e.status;  // 400
    e.message; // "name: too short"
  }
}
```

Branch on `error.code`, not on `error.message`. Codes are stable; messages are not.

`JunjoError` also carries `requestId` (quote it in bug reports), `retryAfterSeconds` (from `Retry-After`, on `rate_limit_exceeded` and `idempotency_key_in_progress`) and `details`, the envelope's structured detail when the server sends one. Two helpers read `details` for you:

| Helper | Returns |
|--------|---------|
| `isNotActive(err)` | `true` when `err` is a ban or sanction lift's "nothing to lift" answer: `not_found` with `details.reason === "not_active"`. Any other `not_found` is `false`. |
| `memberImportErrors(err)` | The failing rows of a rejected [`members.import`](/sdk/members#importgroupid-input-opts), `[]` for any other error. |

## Safe writes

Every method that writes accepts two more options next to `signal` and `timeoutMs`:

| Option | Methods | Sent as |
|--------|---------|---------|
| `idempotencyKey` | Every write. | `Idempotency-Key: <key>`. A retry with the same key and the same request returns the first answer without running the write again. 1 to 255 printable ASCII characters, no spaces. Kept for 24 hours. |
| `ifMatch` | Member-scoped writes (`members.setMetadata`, `setNotes`, `assignRole`, `removeRole`, `overridePermission`, `clearPermissionOverride`; `groups.kick`, `ban`, `unban`), game bans (`bans.add`, `bans.remove`) and sanctions (`sanctions.add`, `sanctions.remove`). | `If-Match: "<version>"`. Pass the number (`7`), the string (`"7"`) or the `ETag` value as is. A stale version rejects with `precondition_failed` and writes nothing. |

The version to send comes from the object you last read: `Member.version` and `MemberAccess.version` for member-scoped writes, `Ban.version`, `Sanction.version` or [`bans.moderation(userId)`](/sdk/bans#moderationuserid) for game bans and sanctions, which share one moderation version. Member, game ban and sanction events carry the version their write produced as `memberVersion` / `moderationVersion`.

| Code | Status | Meaning |
|------|--------|---------|
| `idempotency_key_reused` | 422 | The key was already used for a different request. Use a new key per distinct write. |
| `idempotency_key_in_progress` | 409 | The first request with this key is still running. Wait `retryAfterSeconds` and send it again. |
| `precondition_failed` | 412 | `ifMatch` names a version other than the current one. Re-read, decide whether the write still applies, and resend with the new version and a new key. |

### Queued writes

The SDK never retries a request on its own. A client that queues writes while offline, or replays them after a failure, stores an idempotency key and the version it saw with each queued write, and sends both:

```ts
import { JunjoError, isNotActive, type UserId } from "@junjo.io/sdk";

// Stored when staff pressed "unban", with the version from Ban.version
// and a key generated once for this job.
interface UnbanJob {
  userId: UserId;
  key: string;
  version: number;
}

async function replayUnban(job: UnbanJob) {
  try {
    await junjo.bans.remove(job.userId, { idempotencyKey: job.key, ifMatch: job.version });
    return { done: true };
  } catch (e) {
    // Nothing left to lift: the lift's goal holds.
    if (isNotActive(e)) return { done: true };
    // Someone moderated the player since the unban was queued. Do not
    // lift a newer ban: hand the current state back to staff.
    if (e instanceof JunjoError && e.code === "precondition_failed") {
      return { done: true, conflict: await junjo.bans.moderation(job.userId) };
    }
    // network_error, timeout, 5xx: keep the job, retry later with the same key.
    throw e;
  }
}
```

The key alone is not enough: the server stores its record right after the write commits, so a crash in between, or a retry more than 24 hours later, runs the write again. `ifMatch` turns that second run into `precondition_failed` instead of a duplicate write. Lifts follow one more rule, described in [Safe retries for queued writes](/api-reference#safe-retries-for-queued-writes).

## Sub-namespaces

The `Junjo` instance exposes typed namespaces for each resource. See the per-namespace pages for the methods inside each.

| Namespace | Methods |
|-----------|---------|
| [`junjo.groups`](/sdk/groups) | CRUD, invites, membership lifecycle, group relationships, sub-group `setParent` / `listChildren`, `subscribe` (SSE). |
| [`junjo.roles`](/sdk/roles) | `create`, `get`, `update`, `delete`, `list`, `getGraph`, entries (`grantPermission`, `revokePermission`, `setEntries`), inheritance (`setParents`). |
| [`junjo.members`](/sdk/members) | Read (`get`, `getById`, `list`, `listForUser`), provisioning (`add`, bulk `import`), metadata / notes (`setMetadata`, `setNotes`), role assignment (`assignRole`, `removeRole`), permission overrides (`overridePermission`, `clearPermissionOverride`, `listPermissionOverrides`), resolver input (`getAccess`). |
| [`junjo.invitations`](/sdk/invitations) | `list`, `get`, `revoke`. Accept and decline live on [`junjo.groups`](/sdk/groups) (`acceptInvitation`, `declineInvitation`). |
| [`junjo.audit`](/sdk/audit) | `list`, `listAll`. |
| [`junjo.webhooks`](/sdk/webhooks) | `verify`, `verifyWithMeta`, `middleware`; `endpoints.{create,list,listAll,update,delete}`. |
| [`junjo.friends`](/sdk/friends) | Friendship list (`list`, `listAll`, `remove`, `getRelationship`, `suggestions`) plus sub-namespaces `requests`, `blocks`, `tags`, `visibility`. |
| [`junjo.bans`](/sdk/bans) | Game bans: `add`, `remove`, `get`, `moderation`, `list`, `listAll`, `history`. |
| [`junjo.sanctions`](/sdk/sanctions) | Game-defined restrictions such as mutes: `add`, `remove`, `list`, `listAll`, `forUser`, `history`, `historyAll`. |
| [`junjo.identities`](/sdk/identities) | Identity linking (`list`, `requestLinkCode`, `redeemLinkCode`, `unlink`) and display names (`setDisplayName`, `findByName`). |
| [`junjo.events`](/sdk/events) | The game stream: `subscribe` (resumable SSE with reconnect), `position`. |
| [`junjo.permissions`](/sdk/permissions#permissionsconfig) | The game's permission settings: `config` (mode and context inheritance). Checks themselves are top-level `can` / `check` / `checkBatch`. |

## Top-level methods

In addition to the resource namespaces, `Junjo` exposes a small set of cross-cutting methods directly on the instance.

| Method | Notes |
|--------|-------|
| [`junjo.can(userId, groupId, permission)`](/sdk/permissions) | Boolean wrapper around `check`. |
| [`junjo.check(userId, groupId, permission)`](/sdk/permissions) | Returns the full `PermissionCheckResult`. |
| [`junjo.export(opts?)`](/sdk/export) | Streams the whole game as parsed records (`GET /v1/export`); needs a key with `canExport`. |
| `junjo.verifyToken(token)` | Delegates to the configured `authAdapter.verifyToken`; returns `{ userId } \| null`. Local to the adapter, no Junjo API round-trip. Throws `JunjoError` code `invalid_config` if no `authAdapter` was passed to the constructor. |
| `junjo.whoami(token)` | Deprecated alias for `verifyToken` (the name collided with the server's `GET /v1/whoami`, which answers a different question). Will be removed at 1.0. |
| `junjo.keyInfo()` | Asks the server which game the configured API key belongs to (`GET /v1/whoami`). Useful as a connectivity and credential check during setup and in health probes. In proxy mode it works only if your backend proxy forwards `GET /v1/whoami`. |
